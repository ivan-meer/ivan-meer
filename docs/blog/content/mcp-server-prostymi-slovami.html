Model Context Protocol (MCP) — это не просто протокол. Это USB-C для AI-инструментов. Стандарт, который позволяет подключать любые инструменты к LLM без настройки API-ключей, без написания кода адаптеров, без ручного конфигурирования каждого сервиса.

Разберёмся, как это работает, на пальцах — от пользовательского опыта до внутреннего устройства протокола.

Как это выглядит со стороны пользователя

Для пользователя MCP — это как USB-C. Вы подключаете инструмент — и он работает. Без настройки, без API-ключей, без кода.

Вот как это выглядит в Claude Code:

  1. Пользователь пишет: «найди в проекте все функции, связанные с авторизацией, и покажи их сигнатуры»
  2. Claude Code определяет, что нужен MCP-сервер для работы с файловой системой
  3. MCP-клиент отправляет запрос серверу
  4. Сервер читает файлы, находит нужные функции, возвращает результат
  5. Пользователь видит результат — как будто это сделал сам Claude
Пример из AdminHero

Я подключаю MCP-сервер для базы знаний Postgres. Одна строка в конфиге — и агент может выполнять SQL-запросы, анализировать схемы таблиц, генерировать миграции. Без настройки ORM, без написания API-эндпоинтов, без риска SQL-инъекций — MCP-сервер сам контролирует, какие запросы разрешены.

Как это выглядит со стороны разработчика

Для разработчика MCP — это JSON-RPC сервер с универсальным протоколом. Вот минимальная реализация:

# mcp_demo.py — минимальный MCP-сервер
from mcp.server import Server, NotificationOptions
from mcp.server.models import InitializationOptions
from mcp.types import Tool, TextContent
import mcp.server.stdio

class FilesystemMCPServer:
    """MCP-сервер для работы с файловой системой."""

    def __init__(self):
        self.server = Server("filesystem-mcp")
        self._register_tools()

    def _register_tools(self):
        """Регистрация инструментов, доступных через MCP."""

        @self.server.list_tools()
        async def list_tools() -> list[Tool]:
            return [
                Tool(
                    name="read_file",
                    description="Читает содержимое файла по пути",
                    inputSchema={
                        "type": "object",
                        "properties": {
                            "path": {"type": "string", "description": "Путь к файлу"}
                        },
                        "required": ["path"]
                    }
                ),
                Tool(
                    name="list_directory",
                    description="Списывает содержимое директории",
                    inputSchema={
                        "type": "object",
                        "properties": {
                            "path": {"type": "string", "description": "Путь к директории"},
                            "recursive": {"type": "boolean", "description": "Рекурсивный обход", "default": False}
                        },
                        "required": ["path"]
                    }
                )
            ]

        @self.server.call_tool()
        async def call_tool(name: str, arguments: dict) -> list[TextContent]:
            if name == "read_file":
                content = self._read_file(arguments["path"])
                return [TextContent(type="text", text=content)]
            elif name == "list_directory":
                entries = self._list_directory(arguments["path"], arguments.get("recursive", False))
                return [TextContent(type="text", text="\n".join(entries))]

    def _read_file(self, path: str) -> str:
        with open(path, "r", encoding="utf-8") as f:
            return f.read()

    def _list_directory(self, path: str, recursive: bool = False) -> list[str]:
        import os
        results = []
        for root, dirs, files in os.walk(path):
            level = root.replace(path, "").count(os.sep)
            indent = "  " * level
            results.append(f"{indent}{os.path.basename(root)}/")
            for file in files:
                results.append(f"{indent}  {file}")
            if not recursive:
                break
        return results

    async def run(self):
        async with mcp.server.stdio.stdio_server() as (read_stream, write_stream):
            await self.server.run(
                read_stream,
                write_stream,
                InitializationOptions(
                    server_name="filesystem-mcp",
                    server_version="1.0.0",
                    capabilities=self.server.get_capabilities(
                        notification_options=NotificationOptions(),
                        experimental_capabilities={},
                    ),
                ),
            )

if __name__ == "__main__":
    import asyncio
    server = FilesystemMCPServer()
    asyncio.run(server.run())

Аналогия: REST — это доставка, MCP — это ресторан

REST — это доставка. Вы заказываете через API — и получаете ответ. Каждый раз вы сами выбираете, что заказать. Разные рестораны — разные API. Чтобы заказать из трёх ресторанов, нужно знать три разных API.

MCP — это ресторан. Вы садитесь за стол, берёте меню (инструменты), делаете заказ (JSON-RPC запрос) — и официант (MCP-сервер) сам разбирается, как это приготовить. Один интерфейс для любого «ресторана».

Разница ключевая: REST интегрирует данные, MCP интегрирует возможности. REST говорит «дай мне данные по этому URL». MCP говорит «сделай это для меня».

Демо: MCP-сервер для файловой системы

Выше я показал код сервера. Теперь — как это выглядит со стороны клиента (Claude Code или другого MCP-хоста). Запрос к MCP-серверу — это JSON-RPC сообщение:

// Запрос к MCP-серверу (со стороны клиента)
{
  "jsonrpc": "2.0",
  "method": "tools/call",
  "params": {
    "name": "list_directory",
    "arguments": {
      "path": "/data/projects/adminhero",
      "recursive": true
    }
  },
  "id": 1
}

// Ответ от MCP-сервера
{
  "jsonrpc": "2.0",
  "result": {
    "content": [
      {
        "type": "text",
        "text": "docs/\n  architecture.md\n  api-spec.md\n  README.md\nsrc/\n  main.py\n  utils/"
      }
    ]
  },
  "id": 1
}

Вся магия в том, что клиенту не нужно знать, как реализован сервер. Он просто вызывает инструменты по имени. Сервер сам решает, как выполнить запрос — через локальную файловую систему, S3, SSH или что угодно.

Что внутри протокола

MCP — это не просто JSON-RPC. Это полноценный протокол с несколькими уровнями:

Прикладной уровень

MCP определяет три основных типа возможностей (capabilities):

  • tools — исполняемые инструменты (чтение файлов, запуск команд, вызов API)
  • resources — чтение данных (файлы, конфиги, схемы БД)
  • prompts — шаблоны промптов с динамическими параметрами

Каждый запрос проходит стандартный жизненный цикл:

# Жизненный цикл MCP-запроса
1. Инициализация — клиент и сервер обмениваются возможностями
2. Список инструментов — клиент запрашивает, что умеет сервер
3. Вызов инструмента — клиент вызывает конкретный инструмент
4. Выполнение — сервер выполняет операцию
5. Ответ — сервер возвращает результат (текст, ресурс, ошибку)
6. Завершение — соединение закрывается

Часто спрашивают: «Чем MCP отличается от обычного API? От плагинов? От SDK?». Давайте разложим.

MCP не заменяет API. MCP — это универсальный слой поверх API. Вместо того чтобы писать клиент для каждого сервиса отдельно, вы подключаете MCP-сервер, а он уже разбирается с конкретной реализацией.

Зачем MCP именно сейчас

MCP появился не на пустом месте. К 2025 году стало очевидно, что интеграция LLM с внешними инструментами — главный bottleneck. Каждый раз писать adapter под новый сервис — путь в никуда.

Четыре причины, почему MCP нужен именно сейчас:

1. Универсальный интерфейс

Один интерфейс для всех сервисов. Разработчик не пишет код интеграции — он конфигурирует MCP-сервер. LLM-агент не знает, как устроен сервис — он просто вызывает инструмент через MCP.

2. Безопасность

MCP-сервер работает в изолированной среде. Он сам контролирует, какие запросы разрешены, какие операции доступны. Агент не может выполнить SQL-инъекцию или прочитать файл вне разрешённой директории — MCP-сервер этого не позволит.

3. Масштабируемость

Добавление нового инструмента = добавление одной функции в MCP-сервер. Не нужно писать API, документировать эндпоинты, настраивать авторизацию. MCP-сервер сам регистрирует инструменты.

4. Интеграция с экосистемой

Claude Code, VS Code, Cursor, JetBrains — все IDE поддерживают MCP «из коробки». Подключил сервер — и он доступен везде, где есть MCP-клиент.

Экосистема MCP

MCP — это не просто протокол, а целая экосистема. На момент написания статьи (август 2026):

  • Claude Code — полноценная поддержка MCP, автодетект доступных инструментов
  • VS Code — встроенная поддержка через GitHub Copilot Chat

  • Cursor — нативная интеграция с MCP-серверами

Выводы

  1. MCP — это USB-C для AI-инструментов. Универсальный интерфейс, который решает проблему интеграции один раз и навсегда.
  2. MCP — это не замена API, а слой поверх. MCP-сервер инкапсулирует сложность конкретной реализации за стандартным протоколом.
  3. MCP меняет модель разработки. Вместо «написать код интеграции» → «сконфигурировать MCP-сервер».
  4. Экосистема MCP растёт экспоненциально. 500+ серверов, поддержка во всех основных IDE, стандарт де-факто для AI-инструментов.
  5. MCP — это безопасность. Изолированная среда, контроль доступа, защита от инъекций — встроены в протокол, а не добавляются постфактум.
