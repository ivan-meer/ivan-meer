В 2024 году мы перешли от SQL-запросов к RAG-системам. В 2025 — к агентам. В 2026 — к контекстной инженерии. Но что, если контекст — это не просто дополнение к базе данных, а принципиально новая парадигма управления данными?

Когда я говорю «контекст», я имею в виду не историю диалога и не техническое задание для LLM. Я говорю об управлении вниманием — о том, что модель «видит» в каждый конкретный момент. Это не CRUD, это context engineering.

Почему управление контекстом важнее CRUD

CRUD-системы работают с записями. Context engineering работает с аттеншеном — тем, что модель «смотрит» в данный момент. Разница принципиальна: запись в БД лежит там, пока её не прочитают. Токен в контексте — это дефицитный ресурс, который потребляется за миллисекунды.

В CRUD важна консистентность данных. В context engineering важна релевантность и приоритизация. 50 000 токенов контекста — это не «больше данных», это «меньше внимания на каждый токен». Чем длиннее контекст, тем хуже модель фокусируется на ключевом.

Эксперимент

В статье «Needle in a Haystack» (2023) показано: при контексте 4K токенов модель находит «иголку» в 98% случаев. При 128K токенов — в 65%. При 200K — в 45%. Это не теория, это измеренный факт.

От записей к вниманию — смена парадигмы

В традиционных базах данных мы оперируем записями. SELECT, INSERT, UPDATE, DELETE — всё это про отдельные атомарные единицы. LLM не работает с записями. Она работает с токенами и их взаимным вниманием.

Это меняет всё. Вместо того чтобы думать «какие данные мне нужны», мы думаем «какое внимание я хочу направить модели в данный момент». Это как перейти от библиотечного каталога к персональному ассистенту, который решает, что вам показать.

Контекстный пайплайн: извлечение, трансформация, подача

Контекст — это не один процесс, а пайплайн из трёх этапов. Каждый этап решает свою задачу и имеет собственные параметры.

Этап 1: Извлечение

Сбор данных из всех источников. Это могут быть базы данных, API сторонних сервисов, файлы на диске, веб-страницы. Главная задача — собрать максимум релевантных данных с минимальной задержкой.

class Extractor:
    """Извлекает данные из всех источников."""

    def __init__(self, sources: list[DataSource]):
        self.sources = sources

    async def extract(self, query: str) -> list[RawData]:
        results = []
        for source in self.sources:
            try:
                data = await source.fetch(query)
                results.append(data)
            except SourceUnavailable:
                logger.warning(f"Source {source.name} unavailable")
                continue
        return results

Этап 2: Трансформация

Превращение сырых данных в контекст, который модель может эффективно использовать. Чанкинг, саммаризация, фильтрация, токенизация, эмбеддинги.

class Transformer:
    """Трансформирует сырые данные в контекст."""

    def __init__(self, strategy: ChunkStrategy, compressor: Compressor):
        self.strategy = strategy
        self.compressor = compressor

    def transform(self, data: list[RawData], budget: int) -> Context:
        chunks = []
        for item in data:
            chunks.extend(self.strategy.chunk(item.content))

        # Сжимаем, если превышен бюджет
        if sum(len(c) for c in chunks) > budget:
            chunks = self.compressor.compress(chunks, budget)

        return Context(chunks=chunks, metadata=self._build_metadata(data))

Этап 3: Подача в LLM

Финальная сборка контекста с учётом бюджета токенов, резервирование места под ответ, добавление системного промпта.

class ContextBuilder:
    """Собирает финальный контекст для подачи в LLM."""

    def build(
        self,
        system_prompt: str,
        working_memory: list[Message],
        retrieved_chunks: list[str],
        facts: list[Fact],
        max_tokens: int = 32000,
        reserve_output: int = 4000,
    ) -> list[dict]:
        budget = max_tokens - reserve_output
        context = [{"role": "system", "content": system_prompt}]

        # Рабочая память: последние сообщения
        token_usage = count_tokens(system_prompt)
        for msg in reversed(working_memory):
            if token_usage + msg.tokens > budget:
                break
            context.append(msg.to_dict())
            token_usage += msg.tokens

        # Чанки из RAG
        for chunk in retrieved_chunks:
            if token_usage + count_tokens(chunk) > budget:
                break
            context.append({
                "role": "user",
                "content": f"Контекст: {chunk}"
            })

        # Факты из семантической памяти
        fact_text = "\n".join(f"• {f.subject} — {f.predicate} — {f.object}" for f in facts)
        context.append({
            "role": "user",
            "content": f"Известные факты:\n{fact_text}"
        })

        return context

Стратегии управления контекстом

Для разных задач нужны разные стратегии. Ниже — четыре основные, с примерами кода и реальными метриками.

1. Sliding Window (Скользящее окно)

Лучшая стратегия для последовательных данных: логи, чаты, потоки событий. Идея проста: храним только N последних элементов, остальное либо выбрасываем, либо суммаризируем.

class SlidingWindow:
    """Скользящее окно с суммаризацией старого."""

    def __init__(self, window_size: int = 6, summary_threshold: int = 32000):
        self.window_size = window_size
        self.summary_threshold = summary_threshold

    def build_context(self, history: list[Message]) -> list[Message]:
        recent = history[-self.window_size:]
        older = history[:-self.window_size]

        if not older:
            return recent

        # Суммаризируем старое, если превышен порог
        if token_count(older) > self.summary_threshold:
            summary = self._summarize(older)
            return [summary] + recent

        return older + recent

    def _summarize(self, messages: list[Message]) -> Message:
        """Сжатие истории в одно сообщение."""
        text = "\n".join(m.content for m in messages)
        summary_prompt = f"Суммаризируй этот диалог в 2-3 предложения:\n{text}"
        # Вызов дешёвой модели для суммаризации
        summary = cheap_llm.invoke(summary_prompt)
        return Message(role="system", content=f"История: {summary}")

2. Саммаризация (Summarization)

Для долгосрочных документов, которые нужно хранить в сжатом виде. Отличается от sliding window тем, что мы не храним оригиналы — только сжатое представление.

class SummarizationStrategy:
    """Стратегия саммаризации с сохранением структуры."""

    def summarize_chapter(self, chapter_text: str, level: str = "detailed") -> str:
        if level == "detailed":
            # 70% сжатие: сохраняем все ключевые факты
            prompt = f"""Сократи этот текст до 30% объёма,
            сохранив все числовые данные, имена, даты и ключевые выводы:

            {chapter_text}"""
        elif level == "brief":
            # 90% сжатие: только суть
            prompt = f"Выдели 3 главных факта из этого текста:\n{chapter_text}"

        return fast_llm.invoke(prompt)

3. RAG (Retrieval-Augmented Generation)

Стандартный подход для динамических знаний. Поиск по документам + реранжировка. Здесь важно: RAG — это не просто «поиск + LLM», это целая экосистема с query rewriting, hybrid search, reranking.

class RAGStrategy:
    """Полноценный RAG с гибридным поиском и реранжировкой."""

    def retrieve(self, query: str, k: int = 5) -> list[Chunk]:
        # 1. Query rewriting
        rewritten = self._rewrite_query(query)

        # 2. Параллельный поиск
        vector_results = self.vector_store.search(rewritten, k=k * 2)
        keyword_results = self.keyword_store.search(rewritten, k=k * 2)

        # 3. RRF слияние
        merged = self._rrf_merge(vector_results, keyword_results)

        # 4. Реранжировка кросс-энкодером
        reranked = self.reranker.rerank(query, merged)

        return reranked[:k]

    def _rewrite_query(self, query: str) -> str:
        """Уточнение запроса через дешёвую LLM."""
        prompt = f"Перепиши запрос для поиска, сделав его более конкретным:\n{query}"
        return cheap_llm.invoke(prompt)

4. Structured Output (Структурированный вывод)

Когда ответ должен соответствовать строгой схеме. JSON Schema, Pydantic модели — это не просто валидация, это способ управления вниманием модели. Чем жёстче схема, тем меньше модель «галлюцинирует».

from pydantic import BaseModel
from typing import Literal

class OrderExtraction(BaseModel):
    """Схема для извлечения данных из заказа."""
    order_id: str
    customer_name: str
    items: list[OrderItem]
    total_amount: float
    currency: str = "RUB"
    status: Literal["new", "processing", "completed", "cancelled"]

class OrderItem(BaseModel):
    name: str
    quantity: int
    price: float

def extract_order(text: str) -> OrderExtraction:
    """Извлекает структурированные данные из текста заказа."""
    prompt = f"Извлеки данные заказа из текста:\n{text}\n\nОтветь строго по JSON-схеме."
    response = llm.invoke(prompt, response_model=OrderExtraction)
    return response

Prompt caching как новая норма

В 2026 году prompt caching — это не экспериментальная фича, а стандарт. Anthropic, OpenAI, Google — все провайдеры поддерживают кэширование системных промптов и общих частей контекста.

Экономия токенов

В AdminHero prompt caching даёт экономию 30–50% токенов на частых запросах. Для сложных задач с повторяющимся системным промптом — до 70%. При цене $3/M токенов Claude 3.5 Sonnet это $500–1200 экономии в месяц на 1000 активных пользователей.

class CachedContextBuilder:
    """Контекстный билдер с кэшированием системного промпта."""

    SYSTEM_PROMPT = """
    Ты — AI-ассистент для разработчиков в AdminHero.
    Отвечай кратко, по делу, с кодом.
    Характер: технический, прямой, без воды.
    """

    def build(self, query: str, context: list[str]) -> list[dict]:
        messages = [
            {
                "role": "system",
                "content": self.SYSTEM_PROMPT,
                # Кэшируем системный промпт на 5 минут
                "cache_control": {"type": "ephemeral", "ttl": 300}
            }
        ]

        for ctx in context:
            messages.append({
                "role": "user",
                "content": ctx
            })

        messages.append({
            "role": "user",
            "content": query
        })

        return messages

Кэширование работает, когда:

  • Системный промпт статичен — не меняется между запросами
  • Примеры в контексте повторяются — few-shot примеры можно кэшировать
  • Большие документы — кодовая база, документация API

Не работает, когда:

  • Каждый запрос уникален — нет повторяющихся частей
  • Контекст меняется случайным образом — нет предсказуемости

Разница между контекстом для разных моделей

Для разных моделей нужны разные стратегии контекста. Слепое копирование подходов между моделями — одна из самых дорогих ошибок.

МодельЛимит контекстаСтратегияБюджет на ответ
Claude 3.5 Sonnet200K токеновБаланс: окно + RAG4–8K токенов
Claude 3.5 Haiku128K токеновМаксимальное сжатие2–4K токенов
Claude 3.5 Opus1M токеновСложные задачи, длинный контекст8–16K токенов
GPT-4o128K токеновАгрессивное сжатие4–8K токенов
Gemini 1.5 Pro2M токеновМинимальная фильтрация8–16K токенов

Ключевое наблюдение: чем больше контекст модели, тем меньше нужно его фильтровать — модель сама разберётся. Но тем дороже каждый запрос. Оптимальная точка — найти баланс между качеством ответа и стоимостью.

Когда контекст НЕ нужен

Не все задачи требуют контекста. Вот честные критерии, когда можно (и нужно) обойтись без context engineering:

  • Математические задачи — если ответ зависит только от входных данных, а не от истории
  • Простые вопросы — «как тебя зовут?», «какая сегодня погода?» — здесь контекст не добавляет ценности
  • Задачи с фиксированным ответом — «переведи на русский: hello», «напиши формулу площади круга»
  • Классификация без истории — если каждый запрос классифицируется независимо
  • Валидация данных — проверка формата, типов, схем — не требует контекста
Практическое правило

Если запрос можно обработать без LLM — обработай без LLM. Context engineering имеет смысл, когда задача требует понимания, обобщения или генерации. Для всего остального — регулярные выражения, схемы валидации, lookup-таблицы.

Выводы

  1. Контекст — это не просто история диалога. Это управление вниманием LLM. Разница между CRUD и context engineering — как между библиотекой и персональным ассистентом.
  2. Контекстный пайплайн — три этапа. Извлечение, трансформация, подача. Каждый этап имеет свои параметры и стратегии.
  3. Для каждой модели — своя стратегия. Sonnet, Haiku, Opus — у каждой свой бюджет токенов и своя оптимальная стратегия.
  4. Prompt caching — стандарт 2026 года. Экономия 30–70% токенов. Если не используете — переплачиваете.
  5. Не все задачи требуют контекста. Математика, простые вопросы, фиксированные ответы — используйте более дешёвые подходы.
