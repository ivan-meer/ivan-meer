Когда мы начинали MusicVerse AI, подход был простым: форма → API → результат. Пользователь описывает музыку, нажимает кнопку, ждёт. Но когда продукт вырос из демо во что-то, чем пользуются каждый день, этот подход перестал работать.

Проблема оказалась не в моделях и не в API. Проблема была в отсутствии архитектуры вокруг промпта.

Что не так с «просто промптом»

Первый вариант AI-помощника лирики выглядел так: пользователь пишет описание → мы формируем промпт → отправляем в LLM → показываем ответ. Просто, быстро, демо работает.

Но в продакшене всплывает реальность:

0
контекста у «голого» промпта — модель не знает жанр, настроение, позицию трека в альбоме
9
инструментов в Studio: написать, продолжить, проанализировать, продюсерский разбор, Suno-оптимизация…
1
Edge Function обслуживает все сценарии — не нужно плодить эндпоинты

Если просто вызывать LLM с текстом пользователя — вы получаете случайный результат. Модель не знает, что этот трек — третий в концептуальном альбоме, что предыдущие два были о расставании, а здесь нужен поворот к надежде. Она не знает жанр, темп, вокальный регистр.

Harness: три слоя вместо одного вызова

Решение — харнесс: архитектурный каркас вокруг модели, который превращает «вызвать API» в инженерный процесс.

Слой 1: UI инструменты как action-пресеты

В Lyrics Studio девять видимых инструментов. Пользователь нажимает «Написать» — и фронтенд собирает запрос с типом smart_generate. Нажимает «Продюсер» — отправляет producer_review. Каждый инструмент знает, какие данные собрать из контекста и какой action отправить.

Это не нативный function-calling LLM. Это намеренное решение: мы контролируем, какие действия доступны, какой контекст передаётся и как результат применяется. Модель не решает за пользователя, что делать — она выполняет конкретную задачу с полным контекстом.

Почему не function-calling

Function-calling звучит элегантно в демо, но в продакшене вы хотите предсказуемости. Пользователь нажал «Анализ» — он получит анализ, а не突然 «я решил переписать ваш текст». Action-пресеты дают детерминированный UX при сохранении гибкости: девять инструментов покрывают 95% сценариев работы с лирикой.

Слой 2: контекстный билдер

Перед вызовом модели фронтенд собирает контекст: текущий текст, выбранную секцию, теги, заметки к секциям, style prompt, данные проекта (жанр, настроение, концепция, ЦА, референс-артисты), данные трека (позиция в альбоме, рекомендации), краткий tracklist и историю переписки.

Это критично. Без контекста альбома модель пишет изолированный текст. С контекстом — она знает, что трек №3 должен контрастировать с №2 и подготавливать кульминацию №4.

Слой 3: Edge Function с промпт-реестром

Backend — одна Supabase Edge Function (ai-lyrics-assistant) с реестром промптов. Для каждого action свой системный и пользовательский промпт. Базовый промпт задаёт роль: «элитный автор и продюсер для Suno AI V5» — с полной библиотекой тегов, правилами форматирования и антипаттернами.

Затем добавляется action-специфичный промпт: для full_analysis — строгий JSON-контракт со схемой оценки, для producer_review — коммерческий разбор с хуками и вокальной картой, для validate_suno_v5 — проверка синтаксиса тегов.

Преимущества такого подхода

ПодходРезультат
Голый промптСлучайный текст без контекста проекта, тегов и структуры альбома
Промпт + контекстТекст учитывает жанр и настроение, но не связан с остальными треками
ХарнессДевять специализированных инструментов, каждый с полным контекстом проекта, дающих предсказуемый структурированный результат

Харнесс даёт три вещи, которые невозможно получить «просто промптом»:

  1. Предсказуемость формата. Каждый action возвращает структурированный JSON, который фронтенд парсит и применяет. Пользователь видит карточку результата, а не стену текста.
  2. Контекст альбома. Модель знает, что пишет трек №3 из 12 в концептуальном альбоме — и связывает его с остальными.
  3. Streaming. Текст генерируется токен за токеном через SSE, и пользователь видит, как редактор заполняется в реальном времени.

Технические вызовы

Блокировки в России

MusicVerse — Telegram Mini App, и значительная часть пользователей из РФ. Supabase, OpenAI, Anthropic — всё это работает через прокси и шлюзы. Прямой вызов api.openai.com из России не проходит.

Решение — Lovable AI Gateway как единая точка входа. Мы не обращаемся к Google Gemini напрямую — запрос идёт через ai.gateway.lovable.dev, который маршрутизируется, ретраится и обеспечивает fallback. Edge Function живёт в Supabase Cloud, который доступен из РФ без VPN (через собственную CDN).

Грабли

Первоначально мы пытались использовать несколько провайдеров напрямую с client-side fallback. Это работало 80% времени, но ломалось, когда Telegram WebApp в iOS перехватывал запрос. Перенос всей логики в Edge Function и использование шлюза решили проблему: клиент видит только Supabase, Supabase обращается к шлюзу, шлюз — к модели.

Скорость загрузки в Telegram Mini App

Telegram Mini App — это WebView. На Android это Chrome, на iOS — WKWebView. Разница в производительности — 3-4x. Бандл React 19 + Supabase + Tailwind + framer-motion изначально весил ~2 МБ gzipped, что давало 4-6 секунд первого рендера на 3G.

Что мы сделали:

  • Code-splitting по маршрутам. Lyrics Studio, Studio (DAW), Library, Admin — каждый грузится отдельно. Бандл студии лирики не попадает в основной chunk.
  • Lazy-loading тяжёлых зависимостей. Recharts (графики в админке) грузится только при входе в Admin. 14 компонентов мигрированы на useRecharts() pattern.
  • Streaming генерации. Вместо ожидания полного ответа от LLM (5-15 секунд), мы стримим токены через Server-Sent Events. Пользователь видит, как текст появляется, через ~800ms после нажатия кнопки.
  • Централизованные иконки. Вместо импорта из lucide-react напрямую (что мешает tree-shaking), все иконки реэкспортируются через один barrel-файл с настроенным stroke-width.

Хрупкость JSON-парсинга

LLM нестабильны в форматировании. Gemini 2.5 Flash в 95% случаев возвращает чистый JSON, но в 5% — оборачивает в markdown code fences, добавляет trailing commas или не закрывает скобки. Решение — двухуровневый парсер: backend извлекает JSON регулярками (с greedy-матчом для вложенных объектов), фронтенд нормализует через extractJSON() с fallback на raw text.

// Backend: greedy regex для вложенных lyrics с } внутри
const strictMatch = content.match(/\{[\s\S]*\}(?=\s*$|(?:\s*```\s*$))/);

// Frontend: fallback chain
const data = extractJSON(content);
if (data?.lyrics) return { lyrics: data.lyrics };
if (content.includes("[Verse")) return { lyrics: content };
return null;

Проекты: контекст как первый класс

Харнесс лирики — это не только Studio. В разделе «Проекты» пользователь создаёт альбом: описывает концепцию, целевую аудиторию, жанр, настроение. Добавляет треки — Suno AI рекомендует структуру и теги для каждого. Затем открывает Lyrics Studio из контекста трека — и AI уже знает, что пишет №3 из 12.

Это и есть преимущество харнесса: контекст передаётся автоматически. Пользователю не нужно объяснять модели каждый раз, какой это трек и о чём альбом. Харнесс собирает это из state приложения и упаковывает в промпт.

Выводы

  1. Харнесс — это не про модели, а про контекст. Дешёвая модель с правильным контекстом работает лучше дорогой без него.
  2. Action-пресеты стабильнее function-calling в продакшене. Вы контролируете UX, пользователь получает предсказуемый результат.
  3. Streaming критичен для восприятия. 5 секунд ожидания ощущаются как поломка; 5 секунд стриминга — как живая работа.
  4. Блокировки и скорость — инженерные задачи, не политические. Шлюзы, прокси и code-splitting решают то, что кажется нерешаемым.
